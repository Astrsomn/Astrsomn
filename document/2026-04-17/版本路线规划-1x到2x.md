# Astrsomn 版本路线规划（1.x -> 2.x）

## 目标边界

- `1.0.0`：不包含工作流能力，先把 `provider` 和 `vector` 两组插件做成稳定、可扩展、可运维的核心能力。
- `2.0.0`：在 `1.x` 稳定基础上，引入并发布工作流能力（Workflow）。

## 总体策略

- 以 `0.x` 完成快速迭代与接口收敛，尽早让社区可用并持续反馈。
- `1.0.0` 定义为“核心 AI 平台稳定版”，重点是模型插件与向量插件生态可用。
- `2.0.0` 定义为“工作流增强版”，在稳定核心之上叠加编排能力。

## 里程碑规划

## `0.1.0-alpha.1`（当前起点）

- 完成基础开源发布与项目结构固化。
- 统一扩展元信息维护方式（如 `extension.properties` + `pom` 过滤）。
- 建立 Provider/Vector 的最小可用插件链路（注册、加载、调用、展示）。

## `0.2.0-alpha`

- 聚焦 Provider 组能力补齐：
- 统一模型参数描述、能力声明（chat/embedding/image）。
- 补全多厂商适配一致性（超时、重试、错误码映射、限流语义）。
- 强化配置校验与健康检查。

## `0.3.0-alpha`

- 聚焦 Vector 组能力补齐：
- 完善向量驱动抽象一致性（索引、集合、维度、距离度量、批量写入）。
- 增强数据同步与回填策略（失败重试、幂等、断点续跑）。
- 明确不同向量后端的兼容矩阵与能力差异。

## `0.4.0-beta`

- 进入稳定化阶段：
- 提升集成测试覆盖（Provider/Vector 跨模块联调）。
- 完善插件生命周期管理（安装、启停、卸载、升级回滚）。
- 增加运维可观测性（日志、指标、追踪、告警事件）。

## `0.5.0-rc.1`

- 发布候选：
- 冻结核心接口，清理破坏性变更。
- 进行兼容性回归和性能基线验证。
- 输出正式用户文档与迁移说明。

## `1.0.0`（核心稳定版，不含 Workflow）

- Provider 组达到生产可用：
- 插件规范稳定、主流模型厂商可覆盖、故障处理策略清晰。
- Vector 组达到生产可用：
- 数据接入、向量化、检索、管理链路稳定，性能指标可复现。
- 明确 SLA/SLO 建议、版本兼容策略与 LTS 维护节奏。

## `1.x`（稳定迭代线）

- 仅做非破坏增强与 bugfix：
- 新增插件能力、优化性能、提升可运维性。
- 不引入工作流引擎到主发布定位中。

## `2.0.0`（Workflow 正式引入）

- 引入工作流编排能力：
- 节点编排、执行引擎、上下文管理、重试补偿。
- 与 Provider/Vector 深度集成：
- 把模型调用、检索增强、工具调用纳入统一流程编排。
- 提供迁移路径：
- 从 `1.x` 到 `2.0.0` 的配置与接口升级指南。

## `1.0.0` 发布准入标准（重点）

- Provider 与 Vector 两组插件必须满足：
- **稳定性**：核心链路压测与长稳测试通过，关键故障有降级策略。
- **一致性**：同类插件配置项和行为语义一致，错误模型统一。
- **可观测性**：关键调用链可追踪，核心指标可监控，问题可定位。
- **文档化**：接入、配置、排障、升级指南完整。
- **可扩展性**：新增厂商/后端可按标准模板快速落地。

## 版本号建议（SemVer）

- 当前建议使用：`0.1.0-alpha.1`
- 演进建议：
- `0.1.0-alpha.N` -> `0.2.0-alpha` -> `0.3.0-alpha` -> `0.4.0-beta` -> `0.5.0-rc.1` -> `1.0.0`
- 工作流进入主线后：`2.0.0`

## 执行建议

- 每个小版本固定一个“主题目标”（例如只攻 Provider 或只攻 Vector）。
- 每个里程碑都附带可量化验收项（测试覆盖率、性能指标、故障恢复时长）。
- 在 `1.0.0` 前避免接口频繁破坏；确需变更时提前发布迁移说明。
