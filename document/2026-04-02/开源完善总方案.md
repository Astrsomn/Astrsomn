# Astrsomn 开源完善总方案

## 1. 目标

在不牺牲现有可用性的前提下，将项目从“工程可运行”升级为“开源可协作、可扩展、可维护”的状态。

## 2. 方案总览

### 2.1 方案 A：生命周期与一致性治理（最高优先级）

- 建立统一扩展状态机：`DISCOVERED -> INSTALLED -> APPLIED -> DISABLED -> UNINSTALLED`
- 统一状态来源：
  - DB 元数据状态
  - 运行时 classloader 状态
  - provider handler 可用状态
- 增加关键动作的事务性保障：
  - 应用失败自动回滚状态
  - 卸载失败保留一致状态并可重试

### 2.2 方案 B：扩展机制收敛

- 明确内置扩展与外部插件的边界：
  - 内置：Spring Bean + AutoConfiguration
  - 外置：SPI + 插件目录加载
- 避免同一能力多种注册方式并存导致行为不可预测。

### 2.3 方案 C：模块职责重整

- 收敛 vector 相关职责（实现与编排分层清晰化）。
- 规整 providers 聚合关系，确保模块声明与实际代码一致。
- 清理重复/过时实现，减少维护面。

### 2.4 方案 D：开源工程化能力

- CI：编译、单测、契约测试、静态检查。
- 文档：架构、扩展开发、插件开发、版本兼容矩阵。
- 版本治理：语义化版本、变更日志、升级说明。

## 3. 成果物清单

- 扩展生命周期设计文档（状态机与事件）
- 插件管理 API 规范（安装/应用/停用/卸载）
- Provider 扩展开发指南
- Vector 与 RAG 模块职责说明
- 开源贡献指南（Contributing + Code Style + PR Template）

## 4. 风险与应对

- 风险：改动面广导致回归  
  应对：分阶段发布，先保证 API 向后兼容，逐步替换内部实现。

- 风险：插件卸载引发运行时异常  
  应对：先引入“停用（disable）”过渡态，再执行实际卸载。

- 风险：贡献者对扩展机制理解偏差  
  应对：提供最小可运行示例与失败案例文档。

## 5. 验收标准（开源前）

- 插件生命周期链路可重复、可回滚、可观测
- `starter + providers + workflow` 的最小示例可以一键跑通
- 至少一套扩展（provider 或 tool）按文档独立开发并接入成功
- CI 全绿，主干无 blocker 级已知缺陷
